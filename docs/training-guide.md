# Training Guide

> **Target platform per enterprise upgrade (Anvil).** The shipped lab code currently
> implements the older churn workload; this document describes the upgraded target.

How to retrain locally, how to add a sensor or machine end to end, and what the promotion
criteria actually are.

## Layout

```
ml/
├── data/
│   ├── raw/sensor_windows.csv          exported sensor windows, health-labeled where
│   │                                   available (lab sample generated by
│   │                                   raw/generate_sensor_windows.py)
│   └── processed/                      written by preprocess.py, not committed
├── ingest/
│   ├── tag_mapping.yml                 versioned OPC-UA tag → machine/sensor/unit
│   └── opcua_client.py                 read-only subscriber + store-and-forward buffer
├── notebooks/01-eda.ipynb              vibration spectra, health-score exploration
├── training/
│   ├── config.yml                      single source of truth for the pipeline
│   ├── preprocess.py                   sensor health checks: flatline, drift, gaps, units
│   ├── signal.py                       FFT, envelope analysis, BPFO/BPFI/BSF/FTF tracking
│   ├── features.py                     windowing, spectral + statistical features
│   ├── anomaly.py                      Layer 1: autoencoder/VAE, reconstruction-error score
│   ├── rul.py                          Layer 2: health-index trajectory → RUL band
│   ├── classify.py                     Layer 3: multi-class fault classification
│   └── train.py                        orchestrates layers 1-3, logs, registers → Staging
└── evaluation/evaluate.py              precision gate: Staging vs Production
```

## Retraining locally

```bash
export MLFLOW_TRACKING_URI=http://10.20.2.30:5000   # or http://localhost:5000
make train        # python3 ml/training/train.py
make evaluate     # python3 ml/evaluation/evaluate.py
```

`make train` trains the three layers (anomaly → RUL → classify), registers a new
`anvil-health` version and moves it to `Staging`. It does not touch `Production`.

To run everything offline against a local MLflow, point the tracking URI at a local server
(`mlflow server --backend-store-uri sqlite:///mlflow.db`) — the code paths are identical.

### Offline environment

There is no internet in the plant. Every dependency comes from the mirror on VM12
(`registry-mirror`, 10.20.2.61) — Python packages from devpi (`:3141`), container images
from Harbor (`:5001`). Set these before any training run that needs to install anything:

```bash
export MLFLOW_TRACKING_URI=http://10.20.2.30:5000        # MLflow on VM06
export PIP_INDEX_URL=http://10.20.2.61:3141/root/pypi/+simple/   # devpi on VM12
export PIP_TRUSTED_HOST=10.20.2.61
export DOCKER_REGISTRY=10.20.2.61:5001                   # Harbor on VM12
```

Never point pip or a container pull at a public index — it cannot be reached, and a
transient hang will time out the training job. The APT sources on every host point at the
aptly mirror on VM12 for the same reason.

For a reproducible run matching CI, use the training image (pinned tag — there are no
`latest` tags in an air gap), pulled from the mirror:

```bash
docker pull 10.20.2.61:5001/mlops-training:1.2.0
docker run --rm \
  -e MLFLOW_TRACKING_URI=http://10.20.2.30:5000 \
  -e PIP_INDEX_URL=http://10.20.2.61:3141/root/pypi/+simple/ \
  10.20.2.61:5001/mlops-training:1.2.0
```

Offline CI: the Jenkins pipeline on VM02 (`cicd/Jenkinsfile`) does exactly this — runs
`train.py` on VM11 (`training`, 10.20.2.60, GPU-optional), pushes images to Harbor, and
never touches a public registry.

## Configuration

Everything tunable lives in `ml/training/config.yml` — hyperparameters, the experiment
name, and the bearing-geometry table (BPFO/BPFI/BSF/FTF constants per machine) — and is
logged to MLflow as run parameters, so any run can be traced back to the exact
configuration that produced it.

```yaml
mlflow:
  tracking_uri: "http://10.20.2.30:5000"
  experiment_name: "anvil-health"
  model_name: "anvil-health"
  artifact_path: "model"

data:
  raw_path: "ml/data/raw/sensor_windows.csv"
  test_size: 0.2
  random_state: 42
  target: "health_label"      # Layer 1 is unsupervised; labels feed Layers 2-3

evaluation:
  max_precision_regression: 0.01
```

Change hyperparameters, window length, thresholds or the bearing-geometry table here, not
in the Python — the values are read at run time and logged verbatim.

## Adding a sensor or machine

A sensor has to be added in six places or the serving layer will break at inference time.

1. **Tag mapping** — add the tag in `ml/ingest/tag_mapping.yml`
   (`PLANT2.LINE3.PUMP7.VIB_AXIAL → machine_id=P7, sensor=vibration_axial, unit=mm/s`).
   Unmapped tags are alerted on, never silently dropped, so a missing mapping will surface
   on VM07's `unmapped_tags` counter.

2. **Data** — make sure the sensor stream lands in `sensor_telemetry` (via VM07) and the
   exported window in `ml/data/raw/sensor_windows.csv` carries the new column.

3. **Config** — add the sensor under the feature lists in `ml/training/config.yml`.
   `features.py` builds the windows from these lists, so nothing else in the training
   code needs to change.

4. **Validation** — if the channel must never flatline or has a bounded range, add the
   check in `ml/training/preprocess.py` alongside the existing sensor health checks.
   Failing early during training is much cheaper than a silent distribution shift.

5. **API schema** — add the sensor array to the `sensors` dict in `PredictRequest` in
   `api/app/schemas.py` with the same window-length constraint. **This step is
   mandatory**: the request is serialised into the model's window input, so a sensor
   missing from the schema is a feature missing from the model input.

6. **Tests** — extend `api/tests/test_predict.py` so the new sensor is exercised (valid
   value, wrong array length → 422, missing sensor → 422).

Then retrain: a new model version is registered, and only after promotion do the pods pick
it up. Because the API image is code-only, step 5 requires an image rebuild while steps
1-4 do not.

A new *machine* is simpler: add it to the tag mapping, add its bearing-geometry row in
`ml/training/config.yml` (needed for the BPFO/BPFI/BSF/FTF tracking), and confirm its
alert-tier thresholds. No code change.

### Windows the model has not seen

`features.py` builds fixed-length windows; the API rejects a window with missing sensors
or mismatched array lengths with `422` rather than silently imputing. A sensor that
flatlines for hours should be excluded at the `preprocess.py` layer (`SensorFlatline`
alert) before it ever reaches the model — a model silently trained on a flatlined channel
is worse than no model.

## Promotion criteria

| Transition | Trigger | Criterion |
|---|---|---|
| new version → `Staging` | automatic, at the end of `train.py` | none — every trained model is registered |
| `Staging` → `Production` | manual approval (Jenkins `input` step, or `train-and-register.sh --promote`) | `evaluate.py` must pass |

`evaluate.py` scores the `Staging` model and the current `Production` model on the same
held-out window set and computes alert precision against work-order outcomes
(`work_order_feedback`: a Plan/Urgent/Stop alert closed out as `confirmed_*` is a true
positive; `no_fault_found` is a false positive):

```
threshold = production_precision - max_precision_regression      # 0.01
promotable = staging_precision >= threshold
```

Exit codes:

| Code | Meaning |
|---|---|
| `0` | Promotable — precision holds within the 1% tolerance (or there is no Production model yet) |
| `1` | No `Staging` model found — nothing to evaluate |
| `2` | Precision regressed beyond tolerance — the CI/CD `Train` stage fails here and no approval is offered |

Alert precision is the gate metric rather than F1 or accuracy because the cost of a false
negative is destroyed equipment, not a lost customer, and the platform's own success
metric is false-alarm rate (< 25% target at 12 months). Health-score threshold and
reconstruction-error statistics are logged alongside it for context but do not gate. Both
models' precision, for both stages, are logged to an MLflow run named `evaluate-staging`,
so every promotion decision is auditable after the fact.

## Where the artifacts live

- **Runs, parameters, metrics** — MLflow on VM06 (`mlflow`, 10.20.2.30), backed by the
  `mlflow` TimescaleDB database on VM08 (survives a VM06 rebuild).
- **Model artifacts** — MLflow artifact store on VM06's disk (optionally a plant NAS
  mount). There is no object storage such as S3/GCS in an air gap.
- **Registered versions and stages** — MLflow Model Registry (the source of truth for what
  is serving; `ml/models/` is local scratch only).
- **Training data** — `sensor_telemetry` hypertable on VM08 plus exported windows in
  `ml/data/raw/`.
- **Prediction history** — `predictions` table in the `mlops` database on VM08.
- **Labels** — `work_order_feedback` table on VM08, fed by the technician close-out form
  through the CMMS bridge; this table is what makes the next model version better.
