## Model and features

- **Problem**: remaining useful life (RUL) and anomaly detection on rotating equipment —
  pumps, compressors, motors, gearboxes, and their bearings. Multivariate time series, not
  tabular rows.
- **Architecture**: three layers, trained by `train.py` in order —
  1. **Layer 1 (anomaly)**: autoencoder/VAE trained on known-healthy windows;
     reconstruction error becomes the health score (healthy data reconstructs well, novel
     behaviour does not). Complemented by classical signal processing: FFT and envelope
     analysis with amplitude tracking at the bearing defect frequencies BPFO/BPFI/BSF/FTF,
     computed from bearing geometry and shaft speed.
  2. **Layer 2 (RUL)**: health-index trajectories fitted on failure history and
     extrapolated to a failure threshold. Output is a *distribution* over remaining useful
     life — `lower`/`upper`/`confidence` — never a false-precision point estimate.
  3. **Layer 3 (classify)**: supervised multi-class fault classification (bearing wear,
     misalignment, imbalance, cavitation, looseness). Realistically only after 18-24 months
     of operation and labelled events.
- **Input**: fixed-length windows over the sensor streams `vibration_axial_mms`,
  `vibration_radial_mms`, `temperature_c`, `current_a`, plus `shaft_speed_rpm` for the
  bearing-frequency tracking.
- **Labels are scarce**: Layer 1 works unsupervised from day one. Labels come from the
  work-order feedback loop (`work_order_feedback`), where technicians close out alerts
  with a structured result — that loop is what makes the model improve over time.
- **Evaluation metric**: alert precision against work-order outcomes — a Plan/Urgent/Stop
  alert confirmed by `confirmed_*` feedback counts as a true positive; `no_fault_found`
  is a false positive. False-alarm rate target is < 25%; the promotion gate is a 1%
  precision-regression tolerance. Accuracy/F1 are not used — a false negative here means
  destroyed equipment, not a lost customer.
- **GPU**: optional on VM11 (`training`, 10.20.2.60) for the autoencoder training; the
  classical Layer-1 path runs fine on CPU.

## Air-gap and reproducibility

- **No external registries.** Nothing is pulled from the internet: the training image
  comes from the Harbor mirror on VM12, Python packages from devpi, OS packages from
  aptly. Model updates are artifacts in the local MLflow registry on VM06 — they never
  require a package or image update, which is what keeps the system improvable inside the
  air gap.
- Every hyperparameter, the dataset path, and the bearing-geometry table come from
  `ml/training/config.yml`, which is committed and logged to MLflow as run parameters.
- `random_state: 42` fixes the window split.
- Versions are pinned; there are no `latest` tags anywhere. `docker/training/Dockerfile`
  pins the Python version and library set, so a rerun on VM11 months later produces the
  same model.
- Re-running `scripts/train-and-register.sh` (manually or on the CI/CD schedule) is the
  demonstration of the reproducible-training requirement.

## Promotion criteria

From `ml/training/config.yml`:

```yaml
evaluation:
  max_precision_regression: 0.01
```

A new version may be promoted only if its alert precision (measured against
`work_order_feedback` outcomes on the held-out window set) is at least
`production_precision - 0.01`. Anything worse fails the pipeline before the approval gate
is even offered. When there is no `Production` model yet (first ever run), evaluation
passes automatically.
